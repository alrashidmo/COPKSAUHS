1. System Overview

The College of Pharmacy platform is a single-page web application (SPA) built with vanilla JavaScript, hosted on Vercel, with Supabase as the backend database and authentication provider. There is no separate server — all database operations happen directly from the browser using the Supabase JavaScript client.

ComponentTechnologyPurpose
FrontendHTML + Vanilla JavaScriptAll UI rendering
HostingVercelStatic file hosting, auto-deploys from GitHub
DatabaseSupabase (PostgreSQL)All data storage
AuthenticationSupabase AuthLogin, sessions, user management
File StorageSupabase StorageResearch documents, uploads
Source ControlGitHub (alrashidmo/COPKSAUHS)Code versioning & deployment trigger
Total Supabase tables: 41 across all platform modules. Every table uses Row Level Security (RLS) — all queries must come from an authenticated user.

2. Architecture & Key Concepts

2.1 The Two Types of User ID

This is the most important concept to understand. There are two different IDs for each user:

ID TypeWhere It Comes FromExample ValueUsed In
Auth UUID
user_profiles.user_id		 Supabase Auth — auto-generated when account is created a3f8d2c1-7b4e-... rotation_preferences, rotation_assignments, student_compliance, student_sple_scores, alumni_mentorship_pairs
College Student ID
user_profiles.student_id		 Manually entered during signup (university ID number) 442001234 Display purposes, CSV imports
Critical Rule: All APPE Hub operational tables (assignments, preferences, compliance, SPLE) use the Auth UUID as student_id. Never use the college student number as a database key.

2.2 Academic Year Filtering

All APPE operational tables include an academic_year column (e.g., '2025-2026'). The hub supports three years simultaneously: 2024-2025, 2025-2026, 2026-2027.

  • The active year is stored in rotation_settings.academic_year — this is where new data is written
  • Admins can view any year using the year dropdown in the APPE Hub header
  • Student portal submissions are automatically tagged with the active year

2.3 Student Source of Truth

The user_profiles table is the single source of truth for students.
The APPE Hub builds its student list from user_profiles filtered by class_year = 'P4' and status != 'alumni'. There is a legacy students table that is no longer the primary source.

2.4 Approval Workflow

1 Student fills signup form → row inserted into pending_signups with status = 'pending'
2 Admin sees it in Admin Hub → clicks Approve
3 Database function approve_signup_request() runs → creates Supabase Auth account + row in user_profiles
4 pending_signups.status updated to 'approved'
5 Student can now log in

9. Key Data Flows

9.1 Student Signup → Login

1
Student fills signup form → supabase-auth.js signUp() checks for duplicate email in pending_signups and user_profiles
2
If no duplicate → INSERT into pending_signups with status='pending'
3
Admin sees request in Admin Hub → clicks Approve → supabase-auth.js approveSignup() calls RPC approve_signup_request()
4
DB function creates Supabase Auth user + inserts row into user_profiles → updates pending_signups.status = 'approved'
5
Student logs in → supabase-auth.js signIn() → session created → _restoreSession() retries until AuthSystem is ready → portal shown

9.2 APPE Auto-Match Flow

1
Admin enters scores for P4 students in Scores tab → saved to rotation_assignments (block_number=0, academic_year=_year)
2
Students submit preferences in Student Portal → INSERT into rotation_preferences (student_id = Auth UUID, academic_year = active year)
3
Admin clicks Run Auto-Match → reads rotation_site_availability for block capacity
4
Students sorted by score DESC → each student assigned to 10 blocks respecting preferences and capacity
5
Results UPSERTED into rotation_assignments with conflict key (student_id, block_number, academic_year)
6
Students see their 10-block schedule in Student Portal → rotation_assignments queried by Auth UUID

9.3 Student Progression → Alumni

1
Admin clicks Promote (e.g., P3→P4) in APPE Hub Settings → UPDATE user_profiles.class_year
2
Admin clicks Graduate on a P4 student → UPDATE user_profiles.status = 'alumni'
3
Simultaneously → INSERT into alumni_profiles (checked for duplicate by email first)
4
Student disappears from APPE Hub operations (filtered by status != 'alumni')
5
Student now appears in Alumni Unit → Alumni Directory

10. Row Level Security (RLS)

Every table has RLS enabled. All queries require an authenticated user session.

Policy PatternTables Using ItEffect
auth.role() = 'authenticated'rotation_assignments, rotation_preferences, student_compliance, student_sple_scores, rotation_sites, rotation_evaluationsAny logged-in user can read/write
Student owns their datarotation_preferences (student submit), rotation_evaluations (student submit)Students can only insert/delete their own rows
Public readrotation_sites, college_resourcesVisible to all authenticated users
If a query returns no data unexpectedly, the first thing to check is RLS policies in Supabase → Table Editor → Policies. Missing or restrictive policies are the most common cause of silent data failures.

The Golden Rules

Rule 1: user_profiles.user_id (Auth UUID) is the universal student key across all APPE tables.
Rule 2: Always filter by academic_year when querying APPE operational tables.
Rule 3: rotation_settings row id=1 is the global config — active year + submissions status.
Rule 4: Alumni are excluded by checking user_profiles.status != 'alumni'.
Rule 5: If data doesn't appear, check RLS policies first.
